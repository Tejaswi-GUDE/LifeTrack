### **Slide 8: Feature 5 - Employer Verification**
- **Headline:** One Click. Full Confidence.**
- **The Flow:**
  1. System sends employer a verification link
  2. Employer clicks link → Simple question: "Is this trainee employed?"
  3. If yes: Fills job title + salary range
  4. Trainee's badge updates: L1 → L4 in seconds
  5. Government sees verified outcome in real-time

- **Stats:**
  - Average response time: 2-3 days
  - Confirmed verifications: 85% of sent links
  - Disputed outcomes: 12% (need review)
  - No response: 3%

- **Visual:**
  - Employer dashboard mockup

  - Trainee badge update (before/after)

- **Demo Cue:** Employer role → Show verification link → "One click confirms employment"
- **Speaker Notes:** "Employers verify in seconds. No forms. No manual review. Data flows directly to government. Instant transparency."

### **Slide 17: Data Model**
- **Headline:** Outcome Data That Never Disappears**
- **Core Collections:**
  1. **Trainee** (central record)
     - Name, contact, district
     - Current status (employed, unemployed, etc.)
     - Verification level (L0-L5)
     - Risk scores (outcome risk, attrition risk)
     - Consent preferences

  2. **OutcomeEvent** (append-only history)
     - Trainee ID
     - Event type (employment_start, wage_milestone, job_lost, etc.)
     - Verification level + source
     - Timestamp
     - Note: Never deleted, only appended

  3. **Verification** (employer confirmations)
     - Trainee ID
     - Employer name
     - Claim (role, join date, salary)
     - Response (confirmed, disputed, no_record)
     - Timestamp

  4. **FollowupSchedule** (multi-channel ladder)
     - Trainee ID
     - Current step (WhatsApp, SMS, IVR, Field agent)
     - Attempts history
     - Last contact date

  5. **Evidence** (document uploads)
     - Trainee ID
     - Document type (offer letter, salary slip, etc.)
     - Status (pending, approved, rejected)
     - Reviewer notes

  6. **ConsentRecord** (privacy audit trail)
     - Trainee ID
     - Category (data collection, employer contact, analytics)
     - Granted/revoked + timestamp
     - Who accessed data + when

- **Key Design:** Trainee is central, history is append-only, no data is ever deleted
- **Visual:** Entity-relationship diagram

### **Slide 18: API Architecture**

- **Government APIs:**
  - GET /api/dashboards/government (KPIs, alerts, performance)
  - GET /api/intelligence/market/insights (skill gaps, market demand)

- **Provider APIs:**
  - GET /api/trainees (list with filters)
  - GET /api/dev/phone (mock phone data)
  - POST /api/dev/run-followups (trigger escalation)
  - GET /api/dev/messages/:traineeId (message history)

- **Counsellor APIs:**
  - GET /api/trainees (high-risk list)
  - POST /api/interventions (log action)

- **Employer APIs:**
  - GET /api/verifications/:id (verification link data)
  - POST /api/verifications/:id/respond (submit verification)

- **Verification APIs:**
  - POST /api/verifications/evidence/upload (document upload)
  - POST /api/verifications/evidence/:id/review (approve/reject)

- **Visual:** API hierarchy diagram by role
- **Key Message:** "Clean REST, role-based access control, audit logging on everything"
